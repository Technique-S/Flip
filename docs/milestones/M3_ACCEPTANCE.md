## Adapters and correct boundaries

The adapters use unchanged fixture bytes and the real M2 decoder/resolver with a
deterministic synthetic transport. They never use OpenCode's evaluator/DPLL to
compute a production outcome. Fixture truth tables, witnesses and expectations
remain independent comparison inputs. Synthetic root identities and registry/
environment responses are explicitly test assertions, never claimed deployments.

A02–A06 and the 21 benchmarks use explicit recipes. Exact compiler bytes are
asserted for A02/A03/A04/A06 and all benchmark variants; A05 separately checks
both complete 256-row tables and a native comparison. A01's REF constant
input and B09/B10's constant-only circuits execute as imported compositions behind
a compiled REF wrapper: frozen recipe pins have no general constant-REF pin form.
The original underlying bytes and behavior are still validated and executed.
No new constant-pin schema or generic editor was introduced.

B03 is an unresolved REF, not merely undeclared user intent: it rejects
MISSING_REFERENCE. B11's zero-output case rejects BAD_NETLIST; B12/B13 reject
INVALID_INPUT and B14 BAD_NETLIST. These structured rejections are the safe
production counterparts of the corpus's UNKNOWN/INVALID_INPUT expectations; no
fake proof object is manufactured to match a proposed code.

B17's independent DPLL budget of zero maps to a real supported 1 ms native worker
deadline, producing UNKNOWN/SOLVER_TIMEOUT. It does not claim that Minisat uses
the archival harness's decision counter.

A10/B15 deliberately substitute bytes behind the same REF identity in different
execution contexts. Each closure is independently validated; the real miter/
worker and evaluator confirm the differing behavior (and equivalent alternative
for A10). M2 manifest comparison marks either changed dependency STALE. A single
trusted comparison cannot mix the conflicting identity closures: production
composition rejects IMPLEMENTATION_CHANGED. That stronger identity guard is not
weakened to reproduce a permissive faulty-resolver experiment.

trust. Each case runs through core `consume`, CLI `consume` and the real API route.

Several corpus proposal codes (STALE/UNKNOWN) describe safety outcomes rather
than published error enums. The table records actual frozen-compatible reasons.

replaces the exact source identities, manifests, maps, semantics, dependencies,
engine implementation and native solver binding. Every DIFFERENT from the
production comparison path receives independent direct evaluator replay.

**Critical/high production findings: none confirmed.** No false equivalence,
forged proof acceptance or unreproduced trusted DIFFERENT was observed. This is
bounded acceptance evidence, not an exhaustive security guarantee or solver proof
certificate. Existing native-solver correctness and single-RPC assumptions remain.

## Issues discovered and corrected

The initial merged baseline was **363 passed / 2 failed**. Both failures were
obsolete custody assumptions: the old historical-fixture namespace restriction
and the generic 200 KB tracked-file cap. The exact M3 namespace correction is
hash-pinned; the sole larger-file exception permits only the registered 534,927
byte benchmark file with its full SHA-256. All text still receives secret/binary
review. Original historical gaps remain gaps.

The three immutable M3-B generator files produced **61 Ruff findings**. Their
three exact paths were added to existing archival exclusions, not rewritten or
broadly excluded. Maintained code remains fully linted/formatted; unchanged
generators are executed in scratch with a bounded harness.

The first production adapter run was **66 passed / 4 failed**. One missing-target
transport setup incorrectly looked like an RPC outage; it now models absent
registration explicitly. Three test expectations assumed CLI exit 3 where the
frozen interface correctly returns stale-binding exit 7. Those expectations were
corrected; no engine rejection was relaxed. The next targeted run passed all 75
cases. The complete combined suite and subsequent CI remain the final gates.

## Solver containment, performance and remaining risks

The 21 independent benchmark observations, per-case worker/total time, gate/CNF
counts and explicitly typed memory metrics are in the case report. They are fresh
production runs, not OpenCode's generation-time performance claims. All seven
sizes/modes completed with expected native outcomes; every difference replayed.
In the committed Windows full-suite observations, the 5,000-gate self case used
1,507 ms worker time, 2,083 ms total time and 30,978,048 bytes private-commit peak
(29.54 MiB). Maximum recorded worker time was 1,507 ms and peak private commit
31,236,096 bytes (29.79 MiB). These measurements cover this benchmark family and
host, not arbitrary SAT problems or a production latency guarantee. CI publishes
separate actual Windows/Linux measurements, with their distinct memory metrics.
Resource limits remain 2,500 gates default, at most 5,000 explicitly selected,
depth at most 64, worker wall deadline at most five seconds and memory selection
at most 64 MiB. No admission or expected verdict was weakened for acceptance.

Windows Job objects constrain private commit; Linux RLIMIT_AS constrains virtual
address space. These are distinct metrics, not uniform 64 MiB RSS or aggregate
service containment. Actual allocation pressure, timeout and crash cases run on
each CI platform; all tracked worker processes are reaped and repeated jobs work.
Unsupported platforms fail closed. Parent/HTTP allocations and deployment-wide
quotas remain outside the worker memory cap. Deadline cleanup has ordinary OS
scheduling/reap overhead and is not a real-time guarantee.

Native HTTP verification remains disabled by default and restricted to explicit
trusted loopback opt-in. Public exposure remains blocked pending verified
deployment process isolation, aggregate limits, concurrency quotas and
authentication/rate controls. No malicious-RPC resistance, live CURRENT evidence,
signed proof certificate or globally minimal witness is claimed. Intent, oracle
trust assertions and freshness remain separate from pairwise SAT behavior.

The source-pinned PySAT/MiniSat licensing and notice obligations are unchanged;
see [M3_A_SOLVER.md](M3_A_SOLVER.md). No binaries were vendored. Standalone wheel/
binary redistribution still requires notices for all included solver components.
